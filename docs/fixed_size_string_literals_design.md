# Fixed-Size String Literals for Generated Image Payloads

## Status

- Proposed design.
- Intended as a source-generation optimization for generated C/C++ image
  payloads.
- The change is source-compatible for generated APIs that continue to expose
  the same image accessor functions.

## Objective

Reduce compilation time and generated source size by emitting binary image
payloads as fixed-size string literals instead of comma-separated hexadecimal
initializer lists.

The generated code should keep the exact same binary payload bytes, storage
class, and public image accessor behavior while making the compiler parse much
less source text for large generated icon and bitmap collections.

## Motivation

Large generated image libraries such as `roo_icons` contain many thousands of
small payload arrays. Today each payload is emitted as a list of byte tokens:

```cpp
static const unsigned char ic_filled_24_file_cloud_data[] PROGMEM = {
  0x71, 0x86, 0x18, 0xCE, 0xEC, 0x82, 0x77, 0x10,
  0x06, 0xF9, 0x00, 0x77,
};
```

This representation is readable, but it is expensive for the compiler:

- every byte becomes several tokens,
- every separator and line break must be lexed and parsed,
- generated source files become much larger than the actual payload data, and
- compile time grows with a token stream that contains little semantic value.

The payload data is already compressed binary data. The compiler does not need
to reason about each byte independently. It only needs to place the exact byte
sequence in the selected storage section.

## Background

The importer currently supports generated image payloads for storage modes such
as `PROGMEM` and `SPIFFS`. For `PROGMEM`, generated C++ files commonly define a
payload array near the image accessor function.

The accessor usually constructs a `roo_display` image object over the payload:

```cpp
const RleImage4bppxBiased<Alpha4, ProgMemPtr>& ic_filled_24_file_cloud() {
  static RleImage4bppxBiased<Alpha4, ProgMemPtr> value(
      Box(0, 4, 23, 19), Box(0, 0, 23, 23),
      ic_filled_24_file_cloud_data, Alpha4(color::Black));
  return value;
}
```

Changing the payload literal form should not require changing this accessor
surface. The array symbol should remain usable anywhere a pointer to the first
payload byte is expected.

## Goals

- Preserve the exact generated byte sequence.
- Preserve generated API compatibility.
- Preserve storage annotations such as `PROGMEM`.
- Reduce generated source size.
- Reduce compiler lexing and parsing work for large generated libraries.
- Keep output deterministic and diff-friendly enough for generated artifacts.
- Make the format safe for embedded NUL bytes and trailing bytes.

## Non-Goals

- Changing image compression formats.
- Changing `roo_display` image classes or stream decoders.
- Changing generated accessor names or return types.
- Introducing architecture-specific precompiled binaries.
- Optimizing linker garbage collection behavior.
- Making generated binary data human-editable.

## Requirements

- The array declaration must specify the exact payload size.
- The generated string literal must contain all payload bytes in order.
- The generated array must not include the string literal's implicit trailing
  NUL byte as payload data.
- The emitted C++ must compile on Arduino-oriented toolchains supported by the
  importer.
- The representation must work for payload bytes including `0x00`, `0x22`,
  `0x5C`, and bytes outside printable ASCII.
- The representation must preserve existing storage mode annotations.
- The generator should replace the existing C++ payload array emitter directly;
  no parallel byte-list mode is required for this change.
- The emitter must know the exact payload byte count before writing the array
  declaration. Callers that currently stream bytes without a known final size
  must buffer the payload first or pass an explicit size to the writer.

## Design Overview

For payload arrays, generate a fixed-size character string initializer instead
of a braced byte list.

Current output:

```cpp
static const unsigned char image_data[] PROGMEM = {
  0x00, 0x01, 0x02, 0x41, 0x5C, 0x22, 0xFF,
};
```

Proposed output:

```cpp
static const unsigned char image_data[7] PROGMEM =
    "\x00\x01\x02\x41\x5C\x22\xFF";
```

The explicit `[7]` is essential. Without an explicit bound, C and C++ include
the implicit terminating NUL in the array size. With an explicit bound equal to
the payload length, the initialized array contains exactly the payload bytes.

## Design Details

### Upfront Payload Size Requirement

The current braced initializer can emit an unsized array:

```cpp
static const uint8_t image_data[] PROGMEM = {
  0x00, 0x01, 0x02,
};
```

That form does not require the writer to know the final byte count when it
writes the declaration. The fixed-size string literal form does:

```cpp
static const uint8_t image_data[3] PROGMEM = "\x00\x01\x02";
```

This matters because `hexwriter.HexWriter` currently exposes streaming-style
methods such as `beginStatic(tableName)`, `printHex8(...)`, and
`printBuffer(...)`. The byte count is tracked after bytes are written, but the
array declaration is emitted before the bytes.

For image imports in this repository, this is not a blocker: `Core.write()`
already encodes the image into a `ByteArrayOutputStream` and passes the final
`byte[] encoded` to the C++ definition writer. The new emitter can therefore
write `encoded.length` in the declaration before emitting the string literal.

For other users of this helper code, including font-generation paths that may
stream bytes through `PayloadWriter`, the implementation must avoid assuming
that the existing streaming API is enough. Use one of these approaches:

- buffer the complete payload before calling the C++ literal emitter,
- or change the C++ literal emitter API to require an explicit payload size
  before `beginStatic(...)` writes the declaration,
- or, when generation already writes to a replaceable text buffer, emit a
  declaration-size placeholder and replace it after `getBytesWritten()` is
  known.

This design prefers buffering at the call site when possible because it keeps
the string-literal writer simple and mirrors the current image-import path.
Font-generation code should be checked before sharing this emitter change
beyond image payload generation.

### Font Importer Impact

The font importer in `roo_display_font_importer` depends on
`app/lib/roo_display_image_importer.jar` and imports `hexwriter.HexWriter`.
Changing the shared `HexWriter` therefore affects both generated images and
generated fonts once the jar is updated.

The font path is in `app/src/main/java/roo/display/FontEncoder.java`.
`FontEncoder.writeDefinition(...)` currently:

- creates a `StringWriter buffer`,
- creates `HexWriter hexWriter = new HexWriter(buffer)`,
- encodes all glyph bitmaps into `EncodedGlyph[] encodedGlyphs` before writing
  the font table,
- writes the font table through `hexWriter.beginStatic(var)`,
  `printHex8(...)`, `printHex16(...)`, `printHex24(...)`, and
  `printBuffer(...)`,
- uses `hexWriter.getBytesWritten()` to compute section sizes and `totalBytes`,
- replaces stats placeholders such as `@glyphStats@`, `@headerStats@`, and
  `@totalStats@` in the buffered text, and
- writes the final text to the output `.cpp`.

This structure is compatible with fixed-size string literals, but the array
bound cannot be known at the moment `beginStatic(var)` is currently called
unless the font encoder precomputes it.

There are two practical options.

Preferred low-churn option: support a size expression or placeholder in
`HexWriter.beginStatic(...)`.

For example, add a method such as:

```java
void beginStatic(String tableName, String sizeExpr)
```

which emits:

```cpp
static const uint8_t tableName[sizeExpr] PROGMEM =
```

Then `FontEncoder` can call:

```java
hexWriter.beginStatic(var, "@totalBytes@");
```

and later replace the placeholder alongside the existing stats placeholders:

```java
content = content.replace("@totalBytes@", String.valueOf(totalBytes));
```

This fits the current font-generation architecture because `FontEncoder`
already buffers the entire generated C++ declaration in a `StringWriter` and
already performs placeholder substitution after `totalBytes` is known.

Alternative option: precompute the total font payload size before writing the
array declaration. The required inputs are already available after glyph
encoding:

- `charsetBytes`: 1 for ASCII, 2 for UTF-8,
- `maxFontMetricBytes`,
- `offsetBytes`,
- `glyphs.size()`,
- `font.getKerningPairs().size()`, and
- the sum of all `encodedGlyphs[i].data.length`.

The section sizes are:

```text
headerBytes = 11 + 11 * maxFontMetricBytes + charsetBytes
cmapBytes = glyphCount * charsetBytes
glyphMetricsBytes = glyphCount * (5 * maxFontMetricBytes + offsetBytes)
kerningBytes = kerningPairCount * (2 * charsetBytes + 1)
glyphDataBytes = sum(encodedGlyph.data.length)
totalBytes = headerBytes + cmapBytes + glyphMetricsBytes
           + kerningBytes + glyphDataBytes
```

This avoids placeholder bounds, but it duplicates byte-count logic that
`HexWriter.getBytesWritten()` already verifies during emission. The placeholder
approach keeps `getBytesWritten()` as the source of truth and is less likely to
drift if the font table format changes.

Whichever option is chosen, keep the existing section-stat placeholders and
`getBytesWritten()` checks. They are useful validation that the emitted byte
count matches the declaration bound.

The font encoder also relies heavily on comments emitted through
`HexWriter.printComment(...)`: section comments, glyph comments, kerning-pair
comments, and final statistics. The string-literal writer must preserve this
ability. In practice, each payload line should be a complete string literal, so
comments can appear before it or after it:

```cpp
// Header (24 bytes).
"\x02\x00\x04"

"\x41"  // "A" (U+0041)
```

Adjacent string literals separated by whitespace and comments are still
concatenated by C++, so the generated font payload remains one array
initializer. The writer must not leave an unterminated string literal open when
`printComment(...)` is called.

### Array Type

Keep the existing generated element type unless there is a strong reason to
change it:

```cpp
static const unsigned char name_data[kSize] PROGMEM = "...";
```

`unsigned char` preserves the current pointer behavior and avoids signedness
surprises in downstream code. The string literal initializer is accepted for
character arrays, including `unsigned char` arrays, by the intended C++ usage.

The implementation should keep `unsigned char` and validate the generated
output manually on the intended toolchain before committing the generator
change.

### Escaping Strategy

Emit every byte as a two-digit hex escape in a normal string literal:

```cpp
"\x00\x01\x02"
```

In C and C++, `\x` escapes are technically variable-length: they consume
following hexadecimal digits for as long as possible. That does not create a
risk for the default generated form because every byte starts with a new
backslash. After `\x00`, the next source character is `\`, a closing quote, or
whitespace outside the literal; none of those can extend the previous escape.

Therefore this is safe and is the recommended output:

```cpp
static const unsigned char data[3] PROGMEM = "\x00\xFF\xBA";
```

Splitting is only needed for a future mixed raw/escaped readability mode. The
generator must not place a raw printable hexadecimal character directly after a
`\xNN` escape in the same literal:

```cpp
// Bad: parsed as one larger hex escape, not byte 0x0A followed by 'B'.
"\x0AB"
```

Such a future mixed mode would need to split the literal before any printable
hex digit that follows a hex escape:

```cpp
"\x0A" "B"
```

The proposed default avoids that complexity by escaping every byte and does not
need per-byte splitting.

Octal escapes are also valid:

```cpp
"\000\001\002"
```

Octal escapes have a maximum of three octal digits, so they cannot consume
following bytes. They are slightly more compact in some contexts, but hex maps
more directly to the existing generated byte-list format and is easier to audit.

### Line Wrapping and Indentation

Reuse the generator's existing line-wrapping and indentation policy as much as
practical. This keeps the implementation small and avoids changing generated
formatting more than necessary.

The generator currently controls how many source characters are emitted per
payload line for braced byte lists. The string-literal emitter should use the
same target source-line width, translated to however many `\xNN` escapes fit on
that line.

Example:

```cpp
static const unsigned char image_data[24] PROGMEM =
    "\x00\x01\x02\x03\x04\x05\x06\x07"
    "\x08\x09\x0A\x0B\x0C\x0D\x0E\x0F"
    "\x10\x11\x12\x13\x14\x15\x16\x17";
```

Recommended behavior:

- keep the current target number of source characters per generated line,
- keep the current continuation indentation style where possible,
- semicolon only on the final line.

This is much smaller than the current braced initializer because each byte is
represented by four source characters and the compiler sees one string literal
token per line instead of one numeric literal plus one comma per byte. If hex
output does not produce enough source-size reduction, octal output can be
selected as an additional compact mode.

### Empty Payloads

Empty payload arrays should be generated explicitly:

```cpp
static const unsigned char image_data[0] PROGMEM = "";
```

If a target compiler rejects zero-length arrays, keep the current behavior for
empty payloads or emit a one-byte placeholder and make the associated metadata
carry size zero. Existing importer outputs are not expected to rely on empty
image payloads, so this is primarily a defensive rule.

### Storage Modes

For `PROGMEM`, keep the annotation in the same syntactic position used by the
current generator:

```cpp
static const unsigned char image_data[kSize] PROGMEM = "...";
```

For non-C++ payload storage modes such as generated SPIFFS data files, this
design does not apply unless those modes also emit C/C++ array literals.

### Generated Metadata

When the generator already knows the payload length, emit that length both as
the array bound and, where useful, as a named constant:

```cpp
static constexpr size_t image_data_size = 74;
static const unsigned char image_data[image_data_size] PROGMEM = "...";
```

The named constant makes generated code easier to validate and can support
future descriptor-based APIs. The simpler direct bound is also acceptable:

```cpp
static const unsigned char image_data[74] PROGMEM = "...";
```

## Compatibility

The public generated accessor can remain unchanged:

```cpp
const ::roo_display::Pictogram& ic_filled_24_file_cloud();
```

Only the private payload declaration changes. Existing user code should not
observe a behavioral difference.

Binary compatibility is not a goal for generated source artifacts. Source
compatibility is the important property.

## Validation Strategy

Add generator-level tests that compare payload bytes before and after emission.

Recommended tests:

- a payload containing every byte value from `0x00` to `0xFF`,
- a payload ending in `0x00`,
- a payload containing quotes and backslashes,
- a payload with adjacent hex-looking bytes such as `0x0A, 0x0B, 0x0C`,
- a fixture proving that no printable raw character can extend a `\xNN` escape,
- a representative `ALPHA4` + `RLE` icon payload,
- a representative non-RLE raster payload if C++ array output is used there,
- a representative generated font payload from `roo_display_font_importer`.

For generated C++ tests, compile a small fixture that checks:

```cpp
static_assert(sizeof(image_data) == kExpectedSize);
```

and verifies byte-for-byte equality against the original byte sequence on a
host build.

## Implementation Plan

### Step 1: Replace the payload array emitter

Change the existing C++ payload emitter to write fixed-size string literals
instead of braced hexadecimal byte lists. Do not add a second long-term emitter
mode unless a concrete toolchain issue is discovered.

### Step 2: Make size availability explicit

Update the writer call path so the fixed-size string-literal emitter receives
the final payload length before writing the array declaration. For image
generation, use the already-buffered `encoded.length`.

For font generation, update `roo_display_font_importer` after updating its
`roo_display_image_importer.jar` dependency. Prefer passing a declaration-size
placeholder such as `@totalBytes@` to the writer and replacing it after
`FontEncoder.writeDefinition(...)` computes `totalBytes`. This matches the
font encoder's existing placeholder-substitution flow and avoids duplicating
font table size formulas in production code.

### Step 3: Add tests

Add host tests for escaping, array size, and byte preservation. Include the
full `0x00` to `0xFF` byte range because it catches escape-boundary mistakes.

### Step 4: Regenerate representative outputs

Regenerate representative importer outputs, including `ALPHA4` + `RLE`
pictograms and at least one non-RLE raster image if that path emits C++ arrays.
Regenerate at least one font with `roo_display_font_importer` after refreshing
its `roo_display_image_importer.jar` dependency.

### Step 5: Manually validate before committing

Compile and inspect representative generated output on the intended Arduino
toolchain before committing the generator change.

Measure at least:

- generated source size,
- clean compile time,
- incremental compile time after touching one generated source,
- final firmware size.

The expected firmware size change is neutral. The main expected benefit is
compile-time reduction.

## Risks and Mitigations

### Variable-Length Hex Escapes

Risk: a future mixed escaped/raw literal mode could accidentally emit a
hexadecimal raw character immediately after a `\xNN` escape.

Mitigation: the proposed emitter escapes every byte. Any future mixed mode must
split string literals before raw hex digits that follow a hex escape.

### Toolchain Differences

Risk: embedded C++ toolchains may differ in accepting string literal
initializers for `unsigned char` arrays.

Mitigation: validate the generated output manually on the intended toolchain
before committing the generator change. If a concrete compiler rejects the
form, handle that as a follow-up compatibility fix.

### Debuggability

Risk: generated payloads become less readable than braced hex lists.

Mitigation: these files are generated artifacts. Keep nearby comments with the
image name, dimensions, encoding, compression, and byte count.

### Token Count Tradeoff

Risk: very short line wrapping could still create more string literal tokens
than necessary.

Mitigation: if compile-time measurements show limited improvement, add an
octal or chunked escaped-string mode. A chunked mode can group bytes that are
safe to place in the same literal and split before ambiguous escapes.

## Acceptance Criteria

- Generated payload arrays have explicit bounds equal to the payload size.
- Generated fixed-size string literals preserve payload bytes exactly.
- Existing generated accessors compile unchanged against `roo_display`.
- The implementation does not rely on `PayloadWriter.getBytesWritten()` after
  the declaration has already been emitted; the declaration receives the final
  byte count up front or a placeholder that is replaced with the final byte
  count before writing the generated file.
- `roo_display_font_importer` is updated to use the new size-aware writer API
  after refreshing its `roo_display_image_importer.jar` dependency.
- Generated font arrays use explicit bounds matching `FontEncoder`'s
  `totalBytes`.
- Host tests cover embedded NULs, quotes, backslashes, all byte values, and
  trailing NUL payload bytes.
- Supported Arduino toolchains compile representative generated output.
- A large generated library such as `roo_icons` shows lower generated source
  size and improved clean compile time, with no intended firmware-size growth.
